# RepoPilot 项目最终技术报告

本报告汇总核心修复流程、已验收的 v6 实验、失败分析和本地复现证据。
项目已经从脚本化原型推进到可执行、可验证、可追溯的 Python 仓库修复 MVP；
它不是能够保证修复任意 Issue 的通用开发系统。

本次 P7-S10 收尾使用已有成功/失败案例、报告和复现收据作为交付证据，
**不新录演示视频，不追加模型实验，不修改 v6 分数**。
Git 提交、远程推送或 Release 是否完成，以最终交付记录为准，本报告不作已发布声明。

## 1. 目标与完成范围

RepoPilot 的输入是本地仓库、Issue 和受信配置中的测试命令；输出是补丁、
复现与验证结果、终止原因，以及关联的 Trace 和 artifact。
目标不仅是生成代码，更是回答三个可核验的问题：原问题是否被复现、候选是否真正应用、
当前候选是否通过独立验证。

已实现的主线包括：

- 配置与状态契约、类型化错误、预算与明确终态。
- 基于 LangGraph 的单 Agent 修复流程和受控工具调用。
- 仓库扫描、Python AST/文本切块、BM25、Dense 和 RRF 混合检索。
- 有来源标记的上下文预算、裁剪/摘要、大输出持久化与可读预览。
- Working、Repository、Verified Episodic Memory 及命名空间隔离。
- Docker 执行边界、受限补丁应用、结构化测试结果和独立 Verifier。
- 追加式执行记录、离线 Trace 重放、实验聚合、失败清单与复现文档。

代码入口与职责见 [架构说明](architecture.md)；使用入口见 [README](../README.md)。
Memory 已有实现和契约测试，但本轮真实实验**没有 Memory 消融**。
MCP Adapter 和按需加载 Skill 属于后置 P8，不计为已实现能力；多 Agent、自研推理服务、
SFT 和生产多租户部署也不属于本次完成范围。

## 2. 实际架构与成功条件

系统采用“单 Agent 决策 + 确定性工作流约束”，不是 Master/Sub-agent 架构：

```text
TaskSpec + 仓库 + 配置
  → 初始检索 / 可选 Memory → Sandbox 准备
  → 复现 → 定位与读取 → 应用补丁 → 验证
  → 独立 Verifier → result / trace / artifacts
```

模型选择当前阶段允许的类型化动作；路径、命令、补丁语法、预算、状态迁移和成功判定
由代码执行。`run_tests` 接受任务内测试索引，不接受模型编写的任意 shell。
补丁目标必须先有成功、非空的源文件读取；这证明取得了文件级证据，不证明理解了所有代码。

普通验证失败最多允许一次满足条件的纠错，与空检索恢复共享 replan 预算。
纠错前重读已修改的当前源码；提交的是增量 diff，最终导出的是从原始版本到当前版本的
累计 diff。另有一次受限补丁拒绝纠错，不允许借此绕过通用安全拒绝。

Verifier 要求复现真实测试失败、补丁有应用证据、同一配置命令在最新候选上产生独立且
非空的通过记录。模型自述“已修好”、单纯的补丁落盘、旧版本测试通过都不构成成功。
通过指定回归测试也不等于通过完整上游测试套件。

真实评测额外接入隔离 evaluator：Agent 工作区只含基础源码及自己的修改，
另一工作区承载隐藏回归测试与镜像化的候选修改；只回传脱敏测试摘要。
预期答案不是 Agent 输入，受保护回归测试路径不能被候选修改。
普通 `repopilot repair` CLI 不自动接入此评测器，也不自动继承历史实验的付费授权或总预算。

## 3. 最终真实实验结果

最终接受的是 **8 个已见任务 × 5 个实验臂 × 每槽 1 次执行，共 40 槽**。
它是调试后的已见任务重跑，不是新盲测、40 个独立问题或完整官方 SWE-bench 成绩。

| 实验臂 | 通过 / 计划槽位 | 未成功 / 计划槽位 | 本轮模型估算费用（USD） |
|---|---:|---:|---:|
| Dense only | 4/8（50.0%） | 4/8 | 1.926355625 |
| Hybrid BM25 + Dense + RRF | 6/8（75.0%） | 2/8 | 1.810553750 |
| Mini-SWE-safe，无初始检索 | 5/8（62.5%） | 3/8 | 1.618186875 |
| BM25，无语义 RAG | 4/8（50.0%） | 4/8 | 2.056925000 |
| 单次生成，匹配初始 Hybrid 证据 | 1/8（12.5%） | 7/8 | 0.303288750 |
| 合计 | 20/40（50.0%） | 20/40 | 7.715310000 |

四个交互 Agent 臂合计为 **19/32**，与含单次对照的 **20/40** 分母不同。
全部 40 槽正常结束，技术失败和缺失槽位均为 0/40；24/40 有应用成功的补丁，
20/40 通过配置中的验证。失败没有删除，也没有跨历史轮次挑选最佳结果拼接成功率。

20 个未成功槽位的最终停止机制为：9 次累计 token 上限、3 次验证仍失败、
1 次重复动作，以及单次对照的 3 次 diff 格式拒绝和 4 次应用冲突。
中途错误与最终失败分别统计，不能重复相加。

本轮 v6 已知模型估算费用为 USD 7.715310000；历史带入记账为 USD 22.625591875，
其中 USD 11.00 是未知费用预留。累计应用记账为 **USD 30.340901875 / 50.00**，
不是已核对的 Provider 账单，也不包含 CPU/GPU VM、磁盘等云资源费用。
最终 in-flight response 仍可能使应用限制小幅越界；这不是上游账单硬上限。

### 结果应如何解释

单次对照使用 Hybrid 首次渲染请求中选中的 Issue/仓库证据，但只有一次生成、没有交互工具
反馈；两者的完整提示、计算量和交互预算不同。更重要的是，单次提示只要求普通 unified diff，
解析器却要求 `diff --git` 文件头，三个候选因此被拒绝。这个输出契约混杂没有被隐藏或事后改分。
**75% 对 12.5% 只能描述本版实现，不能宣传为架构带来六倍通用能力。**

每臂只有 8 个已见任务、每题一次执行，不能据此证明统计显著性、结果方差或未见任务泛化。
v5 到 v6 的四个 Agent 臂有 5 槽改善、4 槽退步，净增 1 槽；不能把净增归因于某一个修改。
详细边界见 [评测说明](evaluation.md)和[实验记录](experiments.md)。

文件定位指标只在离线评测端连接冻结 gold 文件名，不使用运行时占位零值。
Mini 初始检索指标为 N/A；Hybrid Recall@5 仅 6/8、MRR 仅 4/8 可恢复，完整实验臂指标仍标 N/A，
不能用可恢复子集的均值与其他完整均值排名。首次相关工具结果耗时也因缺少完成时间戳而为 N/A。

## 4. 关键工程问题与经验

### 4.1 环境可运行不等于真实执行边界可运行

官方任务镜像能在上游 harness 中通过 baseline/Gold 检查，不代表它能直接进入 RepoPilot 的
非 root、只读 rootfs、无网络、不携带 `.git` 的执行边界。实际遇到过 archive 时间戳、
editable build、缺失 `wheel`、`setuptools-scm` 版本推导和测试工具链等兼容性问题。

改进包括分离上游资格检查与自身 Sandbox 检查、批量收集各任务错误、在受信镜像准备阶段固定
依赖，并在真实执行路径验证 baseline 失败和 evaluator-only Gold 通过。一个曾保留 `.git`
的本地探针产生过假阳性，之后修正为验证实际工作区语义。
经验是先区分环境失败、工具实现缺陷与模型失败，再决定修复层级，不能把“某条命令能跑”当作端到端通过。
见[环境调试复盘](p7-s6-environment-debugging-postmortem.md)。

### 4.2 真实仓库规模暴露了小夹具看不到的限制

Django、SymPy 的完整扫描触发过 `listing_truncated`；后续区分内部建库扫描与 Agent 有界列表
能力，并保留不完整语料不能悄悄通过的约束。较大的嵌入工作量采用 GPU 预计算、内容身份绑定和
缓存复用；它改变了准备方式，不等于改变模型、任务或评分，也不能用不同批量/长度的探针声称严格加速倍数。
见[仓库工作量修复记录](p7-s6-repository-workload-repair.md)及
[缓存验收记录](../results/p7-holdout/gpu-cache-preflight-v2.json)。

### 4.3 纠错需要工作区、补丁和验证版本一致

第二次修改必须基于当前源码，累计导出必须包含第一次修改，测试结果必须对应最新候选。
v6 的四次验证失败后纠错都发生在 Flask：均有当前源码重读和第二版应用证据，
其中 Hybrid 第二次验证通过，其他三臂仍失败。流程支持纠错，不意味着它必然改善结果。

事后发现公开 Issue 示例使用 `mode="b"`，冻结测试使用 `text=False`；三个失败候选仍采用
`mode` API。这里能确认接口契约差异，但不能声称 Agent 看见完整隐藏测试却故意忽略它。
隐藏信息只用于离线诊断，没有回填为修复答案。见[失败分析案例 C](error-analysis.md#c-两次补丁都能应用为什么-flask-仍失败)。

### 4.4 上下文限制、累计预算和信息保留是三个问题

9 槽因为累计 token 耗尽而停止，并非单请求上下文超限。有的槽位早已读到相关代码，
却在提出补丁或验证时触发预算。记录还显示，Mini SymPy 的摘要保留扫描元数据，却没有保留
此前符号结果的文件定位；随后发生重复查询。信息缺失和重复共现有证据，但因果关系未验证。

因此后续方向是请求前预算准入、给补丁/验证保留余量、按工具 schema 保留关键信息和有界复用
已有结果，而不是直接放开无限步数、重复调用或扩大权限。这些是未实施、未证明收益的 backlog，
不计入当前完成能力。见[失败分析](error-analysis.md)。

## 5. 验证证据与复现边界

v6 接收审计核对了 40 次执行、80 个历史事件、32 个 Agent Trace、8 个单次对照 Trace，
以及 519 个 artifact 引用；成功链条包含 baseline 失败、补丁应用和新鲜、非空的验证通过。
离线重放检查记录完整性和状态连续性，不重新执行模型或测试，也不是外部服务真实性的密码学证明。
实验执行源固定为 `ff8f7c0144b56749c6d1515ff9c7f83da53680e6`，身份与输入见
[冻结计划](../results/p7-holdout/postdebug-plan-v6.json)。

S9 在新的完整 Git checkout 和独立虚拟环境中完成非付费复现，收据记录：

- 普通离线套件：**2,112 passed，10 skipped，21 deselected**。
- Ruff 检查通过；246 个文件格式检查通过；89 个源文件的 mypy 检查通过。
- 脚本化调查与重放、3 个合成 BM25 任务、成功/失败两个修复契约用例通过。
- 实时 Provider 请求、付费请求、Docker 请求、嵌入模型加载和云端修改均为 0。

这使用已有 Python 3.12.12 和依赖缓存，在 Darwin/arm64 上安装，**不是新操作系统或空缓存安装**。
成功/失败修复用例使用 Fake Provider 和只允许可信小夹具的本地测试适配器；虽实际执行了
`git apply` 和 pytest，但不能冒充自主 LLM 修复、Docker 隔离或新的真实实验成绩。
其中错误补丁的验证失败，最终以 `max_steps` 停止，仍正确保留 `task_success=false`。
来源：[干净目录复现收据](../results/p7-clean-run/receipt-v1.json)。

Git 中保留汇总、逐槽导出、失败清单、计划和收据；完整原始 archive 与本地 demo 产物
不默认公开。独立完整核验需要原始包，新执行还需要私有 registry 镜像访问、冻结运行输入、
模型凭据和缓存/数据库准备。因此“可读报告”“可离线核验”“可重新执行付费实验”是不同层次。
现有核验入口见[评测文档](evaluation.md)，本报告不另设 VM 操作流程。

真实 Trace 中 275 次工具执行没有策略拒绝，只是普通任务观测，不是攻击拦截率。
Docker 不是 VM 边界；模型收到的代码片段可能包含敏感业务信息；哈希不是抵抗恶意本地写入者的签名。
安全单测和历史 Docker 检查有各自范围，不能合成“100% 安全”。见[威胁模型](threat-model.md)。

## 6. 收尾结论与后置工作

本次交付的核心价值是一个受约束、可审计的修复闭环，以及对成功、失败和不可测指标保持同一套
证据标准。P0–P6 的实现、P7 已接受实验、聚合、失败分析及 S9 本地复现都有对应代码或记录。
本报告负责技术总结，不以文档完成代替发布检查，也不以一次测试通过宣称通用正确性。

P8 MCP/Skill 微实验、Memory 效果消融、独立新任务和多次重复评测、单次对照契约修正后的重新比较、
预算/摘要改进及生产化部署均后置。它们不作为本次 P7 收尾的新阻塞项，也没有被计为已完成。
本轮不新增实验、不补录视频、不挑选或修改历史结果；后续若开展工作，应建立新版本和独立验收边界。
